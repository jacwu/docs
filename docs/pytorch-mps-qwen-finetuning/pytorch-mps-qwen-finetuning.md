# 使用 PyTorch + MPS 微调 Qwen售后决策模型

本文以 **Qwen3.5-0.8B 的中文电商售后决策微调**为例，介绍从环境准备、数据组织、小样本验证到正式训练、概率校准和完整测试的流程。模型接收售后政策、订单事实和客户原话，从七个处理动作中选择下一步，而不是生成一段客服回复。本次在 **Apple M5、32 GB 统一内存**的 Mac 上完成训练。正式训练使用 3,738 条数据、1 个 epoch，耗时约 4 小时；在相同输入与评分方式下，2,548 道合成测试题的准确率从基座的 **14.29%** 提高到微调后的 **97.53%**。

## 一、确定任务和技术路线

### 1.1 将售后处理定义为七选一任务

输入由三部分组成：

| 输入 | 含义 | 例子 |
|---|---|---|
| `policy` | 当前适用的售后规则及参数 | 退款时限、证明等级、自动处理金额上限 |
| `records` | 已经核实的订单与售后事实 | 是否扣款、是否缺件、退款状态、库存 |
| `message` | 客户的原始描述 | “这单少了一件，能不能补发？” |

模型输出字段为 `next_action`，候选动作固定为七个：

| 动作 | 含义 |
|---|---|
| `refund_only` | 无需退货的退款流程；重复扣款只退多扣部分 |
| `return_refund` | 退货退款流程 |
| `reship` | 补发或换新 |
| `wait` | 等待现有物流或退款流程 |
| `decline` | 按政策拒绝本次申请或重复退款 |
| `request_info` | 补充订单、证明或诉求信息 |
| `manual_review` | 人工核查或确认方案 |

例如，已核实缺件、证明满足要求、客户要求补发且库存充足时，模型应该选择 `reship`；如果超过自动处理上限，则应转为 `manual_review`。

这种设计将“判断”与“执行”分开。模型只给出处理建议和概率，不直接退款、不修改订单，也不把客户原话自动当作已经核实的事实。

### 1.2 本次采用的训练方式

| 项目 | 方案 |
|---|---|
| 基座 | `Qwen/Qwen3.5-0.8B`，使用文本语言模型部分 |
| 计算框架 | PyTorch |
| GPU 后端 | MPS，即 PyTorch 对 Apple Metal GPU 的支持 |
| 数值精度 | FP32，32 位浮点数 |
| 微调方法 | LoRA，冻结基座，只更新附加的低秩参数 |
| 训练目标 | 七个候选动作的概率分布 |
| 输出方式 | 读取候选答案 token 的 logits，不生成长文本 |

**LoRA** 把权重增量表示为两个较小矩阵的乘积。本次 rank 为 8、alpha 为 16，可训练参数为 **5,411,328，约 541 万**。基座参数保持冻结，也没有额外增加一个独立的分类头。

## 二、准备项目环境与 MPS 加载路径

### 2.1 环境配置

本次运行的主要环境如下。这是实际使用的版本组合，不表示必须追逐最新版本。

| 项目 | 配置 |
|---|---|
| 芯片 / 内存 | Apple M5 / 32 GB 统一内存 |
| 系统 | macOS 26.5.1 |
| Python | 3.12.14，arm64 |
| PyTorch | 2.14.1 |
| Transformers | 5.18.0 |
| PEFT | 0.21.2 |
| 设备 / 精度 | `mps` / `float32` |

环境准备分为三步：

1. 在项目目录创建独立的 Python 虚拟环境，将依赖和模型缓存也保存在项目内。
2. 安装上表中的 PyTorch、Transformers 和 PEFT，同时安装 Accelerate 1.15.0、Safetensors 0.8.0。
3. 检查当前 PyTorch 是否包含 MPS 支持、系统是否能够使用 MPS，并在 MPS 上创建张量完成一次简单运算。

### 2.2 先在 CPU 上加载 FP32，再移动到 MPS

本次加载过程曾在直接向 MPS 加载并转换权重精度时发生原生崩溃。稳定后的路径是：**先在 CPU 完成 FP32 权重加载，再串行移动到 MPS**。

具体加载顺序如下：

1. 准备完整的原始模型文件、tokenizer（分词器）和聊天模板。
2. 从 Qwen3.5 配置中提取文本配置，使用对应的文本语言模型类；本任务不加载图像或视频处理流程。
3. 在 CPU 上以 FP32 加载权重，完成后再将模型整体移动到 MPS。
4. 确认模型参数与后续输入位于同一设备，再开始训练。

CPU 中转不等于训练在 CPU 上执行。后续前向、反向和参数更新仍在 MPS 上进行。本次没有使用 CUDA autocast，也没有依赖静默 CPU fallback 完成训练。部分可选加速内核不可用时，使用普通 PyTorch 实现完成计算，速度相对较慢。

## 三、准备电商售后数据集

### 3.1 数据集的用途与文件

这些数据根据**虚构的售后政策**合成，标签由规则生成，不是真实客户对话，也不代表某个电商平台的实际政策。它适合验证模型对售后规则、事实和处理动作的映射能力；用于真实业务前仍需独立人工审核和真实数据测试。

| [测试集](datasets/after-sales/test.jsonl) | 2,548 | 1,274 | 最终一次性比较 |

数据为 JSONL 格式，即一行一个 JSON 对象。另有 [政策定义](datasets/after-sales/policy_spec.json) 和 [评估切片](datasets/after-sales/evaluation_slices.json)，用于描述规则及按不同场景分别统计结果。

### 3.3 为什么按组划分

两条记录构成一组，用来检查模型是否关注真正影响决策的条件：

- **反事实组**：改变关键政策或事实，正确动作应随之改变，例如把自动处理上限从覆盖本次金额改为低于本次金额。
- **不变性组**：改变不影响当前规则分支的因素，正确动作应保持不变。

同一组不能被拆到训练集和测试集。否则模型可能在训练中见过几乎相同的另一半，测试分数会偏乐观。

本次保留原有四份划分。所有集合的实际最大输入为 **858 tokens**，低于 1,024 的长度上限，没有通过截断删掉政策或订单字段。

## 四、把售后样本转换为模型输入和监督目标

### 4.1 用答案位置读取七个候选的分数

模型不是直接生成 `reship` 这个字符串，而是把七个候选映射到 `A`—`G`，从下一 token 的词表分数中取出这七个答案位置的 logits，再映射回动作名称。

处理过程是：组织售后状态、问题和候选动作，套用聊天模板并分词，完成一次模型前向计算，再通过 softmax 将七个候选分数转换为概率，选择最高概率对应的动作。

必须先确认 `A`—`G` 在当前 tokenizer 中分别对应一个独立 token，且七个 token 的 ID 互不相同。

动作名称只是业务语义，答案位置是模型读出的接口。不能直接把多 token 的动作字符串当成一个词表索引。

### 4.2 重排候选时，目标也必须重排

为了减少模型记住固定位置的倾向，训练时对候选动作顺序进行随机重排，评估时使用固定顺序，并额外测试其他重排。

转换每条完整原始样本时，执行以下步骤：

1. 读取售后状态、下一步动作问题及七个候选说明，不把正确答案放进提示词。
2. 按当前候选顺序分配 A—G，保持动作名称与说明一一对应。
3. 套用聊天模板，关闭思考模式，分词后检查长度；超过上限时先检查数据，不静默截断。
4. 根据正确动作在当前候选中的位置生成 one-hot 目标，即正确项为 1，其余项为 0。

训练以随机种子 42 为基础，结合轮次和样本行号生成可复现的重排。验证和主测试保持固定候选顺序，其他文本增强和额外选项填充均关闭。

假设当前候选顺序为 `decline、manual_review、refund_only、request_info、reship、return_refund、wait`，则补发样本的 one-hot 目标为 `[0, 0, 0, 0, 1, 0, 0]`。重排后应按动作语义重新生成目标，不能沿用旧位置。

## 五、配置 LoRA 与训练损失

### 5.1 只微调文本模型的投影层

本次对文本模型中的线性投影层添加 LoRA，不修改词嵌入和语言模型输出头。按完整模块路径选择目标，避免只匹配短名称时误选同名模块。

通过 PEFT 注入 LoRA，设置 rank=8、alpha=16、dropout=0.05，冻结基座，仅让 LoRA 参数参与更新。开始训练前检查可训练参数数量，并确认梯度能够正常传播。

训练时开启梯度检查点，关闭推理用的 KV 缓存，以减少内存占用。

`gradient checkpointing` 会在反向传播时重新计算部分中间结果，以额外计算换取更低的激活内存占用。它不是保存到磁盘的训练 checkpoint，两者名称相近但用途不同。

### 5.2 损失函数：CE + Brier

本次总损失为 **Loss = CE + Brier**，两部分分别衡量：

- **CE（交叉熵）**：正确动作的概率是否足够高。对于 one-hot 目标，它等于正确动作概率的负对数。
- **Brier**：七项预测概率与 one-hot 目标之间的平方误差之和。本次不再除以类别数，两项损失权重均为 1。

每条样本只保留输入最后位置的词表 logits，取出七个候选的分数，以 FP32 计算概率和损失，再反向传播到 LoRA 参数。这样不必为全部输入位置保留庞大的词表输出张量。

### 5.3 梯度累积与最后一个不足批次

本机一次前向和反向只处理一条数据，即 **micro-batch=1**，累计 8 条的梯度后再调用一次优化器。

一个累积窗口的逻辑为：

1. 清空上一个窗口累积的梯度。
2. 对窗口内每条样本计算损失，除以该窗口实际样本数，再进行反向传播。
3. 对可训练参数做梯度裁剪，最大范数为 1。
4. 使用优化器更新 LoRA 参数，再推进学习率调度。

采用 AdamW，`weight_decay=0`。最后一个窗口只有 2 条时，损失除以 2，而不是固定除以 8，否则最后一次更新会被额外缩小。

## 六、先做小样本验证，再进行完整训练

### 6.1 32 条 smoke：先确认可以更新和保存

先从训练集选择完整组构成的 32 条样本，累计 8 条更新一次，共 4 次优化器调用。检查：

- 损失和梯度是否为有限值。
- 基座是否保持冻结，LoRA 参数是否真的发生变化。
- 保存后能否在新进程中重新加载。
- 重载前后同一组固定样本的 logits 是否一致。

本次 372 个 LoRA 张量发生改变，基座不变；保存后独立重载，固定样本 logits 最大差为 0。这里只确认训练链路正常，不要求 32 条都预测正确。

### 6.2 8 条过拟合诊断：确认模型能学会少量样本

如果模型连少量训练题也拟合不好，直接增加全量训练时间很难判断问题来自数据、标签映射、候选重排还是训练设置。

本次使用固定的 8 道训练题，对候选顺序和学习率进行有界对照。每次重新从原始基座初始化，不从上一次 adapter 继续训练。

| 候选顺序 | 学习率方式 | 优化器调用数 | 固定评估顺序下正确数 | CE | Brier |
|---|---|---:|---:|---:|---:|
| 随机 | 预热 + 余弦衰减 | 40 | 4/8 | 1.480631 | 0.665649 |
| 固定 | 预热 + 余弦衰减 | 40 | 8/8 | 0.447782 | 0.234495 |
| 固定 | 常数 | 40 | 8/8 | 0.253360 | 0.138518 |
| 固定 | 常数 | 160 | 8/8 | 约 4.58×10⁻⁸ | 约 2.00×10⁻¹⁴ |
| 随机 | 常数 | 160 | 8/8 | 约 4.08×10⁻⁷ | 约 3.84×10⁻¹³ |

最终随机顺序训练的 adapter 在固定顺序和三套额外重排中均为 8/8 正确。整个诊断累计 440 次优化器调用，约 5.21 小时。

这些结果说明本次链路可以充分拟合小样本，不表示已经具有新题泛化能力，也不能从单个种子的对照断言某一个设置是唯一原因。

### 6.3 196 条试跑：估算完整训练成本

随后重新从基座和新 LoRA 开始，用 196 条训练数据、1 个 epoch 试跑：

- 25 次优化器调用，最后一个累积窗口有 4 条。
- 训练循环约 16.8 分钟。
- 稳定阶段每次更新耗时中位数约 33.78 秒。
- 全量训练 468 次更新的同速估计约 4.39 小时，不包含后续评估。

试跑用于检查真实长度下的内存、速度、梯度和保存行为，不要求全部样本记住，也不把该 adapter 当作正式训练起点。

### 6.4 先记录基座结果，再进行正式训练

正式训练前，先用不加载 adapter 的基座完成 1,512 条验证集评分。随后从原始基座重新初始化 LoRA 和优化器，完整训练全部 3,738 条数据。

| 参数 | 本次正式配置 |
|---|---|
| LoRA rank / alpha / dropout | 8 / 16 / 0.05 |
| 可训练参数 | 5,411,328 |
| 训练轮数 | 1 epoch |
| micro-batch / 梯度累积 | 1 / 8 |
| 最大输入长度 | 1,024 tokens，实际最大 858 |
| 峰值学习率 | 1×10⁻⁴ |
| 学习率调度 | 3% 预热，之后余弦衰减 |
| 预热步数 | 14 |
| 优化器 / 权重衰减 | AdamW / 0 |
| 梯度裁剪上限 | 1 |
| 损失 | CE + Brier，权重均为 1 |
| 候选顺序 | 逐轮、逐题确定性随机重排 |
| 随机种子 | 42 |
| 保存频率 | 每 50 次更新保存，最后再次保存 |
| 最终模型选择 | 唯一候选，固定使用最终 adapter |

3,738 条数据包含 467 个完整的 8 条窗口和最后一个 2 条窗口，因此一轮训练共调用优化器 **468 次**。

按本次调度器的语义，第一次调用的实际学习率为 0，因此 468 次调用中有 **467 次正学习率调用**。日志应区分“本次实际使用的学习率”和“调度后的下一次学习率”，避免把末尾显示的下一步 LR=0 误认为最后一次没有更新。

正式训练循环耗时约 **3.98 小时**，包含模型加载与训练检查约 **3.99 小时**。全部 3,738 条样本参与训练，没有跳过超长样本。诊断阶段的常数学习率没有直接迁移到正式训练；正式训练使用预先确定的较长余弦周期。

## 七、保存、重载与实际推理

### 7.1 保存的是 adapter，不是另一个完整基座

LoRA 训练完成后，保存 adapter 权重、配置，以及配套的 tokenizer 和聊天模板。

最终 adapter 权重文件为 **21,694,976 字节，约 20.69 MiB**。加载时仍然需要相同的原始基座，不能把这一小份权重单独当成完整模型。

随后在独立的新进程中重新加载原始基座，按相同的 FP32 路径移动到 MPS，再加载最终 adapter，切换到评估模式。不要给已经添加 LoRA 的模型重复套一层 adapter。

本次正式模型重载后，四条固定样本的 logits 与保存前完全一致。只有 adapter 的中间 checkpoint 不能恢复完整的 Adam 状态、调度器和随机状态，因此本次采用阶段级恢复，不把它当作完整训练断点续跑。

### 7.2 用相同的输入转换和读出方式推理

推理仍使用第四节的输入转换，固定候选顺序，关闭 dropout 和梯度计算，从七个 logits 得到概率，再映射回售后动作。如果需要校准概率，则应用第八节确定的温度。

实际请求只需提供售后状态、问题和候选动作，完全不需要正确答案，也不需要包含 `targets` 字段。

本次实际运行的一条验证集案例为：已核实缺件、证明等级 3、客户要求补发且有库存，金额 105 元、件数 2、申请年龄 2 天，均在政策上限内。使用最终模型和原始概率 `T=1`，返回摘要为：

```json
{
  "action": "reship",
  "reship_probability": 0.9999265401809947,
  "inference_seconds": 1.350499000021955
}
```

结果为“补发”，概率约 **99.9927%**。这是固定案例的实际输出，不是额外的独立测试分数；1.35 秒只统计单题推理，不包含模型加载。输出的是动作及概率，不是自然语言客服话术。

## 八、与基座比较，并校准输出概率

### 8.1 基座与微调模型必须使用同一协议

比较时保持以下条件相同：

- 同一份输入、tokenizer、聊天模板和候选顺序。
- 同样的 MPS / FP32 路径、长度上限和 eval 模式。
- 同样的七项 logits 读出、动作映射和并列处理规则。
- 逐题比较，不给某个模型单独修改提示词或重试挑答案。

基座不加载 adapter；微调模型加载基座加最终 LoRA。验证集结果如下：

| 指标 | 基座 | LoRA |
|---|---:|---:|
| 正确题数 | 216/1,512 | 1,484/1,512 |
| 准确率 | 14.29% | 98.15% |
| macro-F1 | 0.035714 | 0.981507 |
| CE | 2.565870 | 0.099138 |
| Brier | 1.053170 | 0.034253 |

基座在本次固定提示词与七选一读出协议下全部选择 `decline`。这一结果描述的是它对当前任务及接口的适配程度，不是对 Qwen 通用语言能力的全面评价。

本次预先固定使用最终 adapter，没有依据验证集成绩反复挑选中间 checkpoint，也没有临时增加训练轮数。

### 8.2 只用校准集调整概率

动作正确率和概率可信度不是同一件事。一个模型可能经常答对，也可能在少量错题上过度自信。

温度校准先将七个 logits 同时除以正数温度 T，再通过 softmax 重新计算概率。

基座与 LoRA 分别在 1,512 条校准集上拟合一个温度，使平均 CE 尽可能小，搜索范围固定为 `[0.1, 10]`：

| 模型 | 温度 T | 校准集 CE：校准前 → 校准后 |
|---|---:|---:|
| 基座 | 10，达到预设上限 | 2.552297 → 1.946818 |
| LoRA | 1.6731661107614562 | 0.139237 → 0.101658 |

两个温度冻结后，才进入最终测试。基座碰到上限时不继续扩大范围，也不使用测试集选择温度。

正温度不会改变 logits 的大小顺序，所以校准用于调整“有多自信”，不负责把错误动作改成正确动作。本次也逐题检查了校准前后动作相同。

## 九、完整测试结果与剩余问题

### 9.1 四组完整对照

基座和 LoRA 各完成全部 **2,548 道测试题**。从两份原始 logits 计算校准结果，不需要为四组结果重复执行四轮模型推理。

| 测试组别 | 准确率 | macro-F1 | CE | Brier | ECE（10 箱） |
|---|---:|---:|---:|---:|---:|
| 基座，原始概率 | 14.29% | 0.035714 | 2.561960 | 1.048733 | 0.370462 |
| LoRA，原始概率 | 97.53% | 0.975240 | 0.146025 | 0.046346 | 0.020467 |
| 基座，温度校准后 | 14.29% | 0.035714 | 1.950714 | 0.858617 | 0.028948 |
| LoRA，温度校准后 | 97.53% | 0.975240 | 0.105361 | 0.042345 | 0.008635 |

其中，macro-F1 是七个动作 F1 的平均值；ECE 将置信度分成 10 个区间，比较平均置信度与实际正确率。CE、Brier 和 ECE 都是越低越好，但任何一个总体指标都不能保证每道题可靠。

LoRA 答对 **2,485 题**，基座答对 **364 题**，准确率提高 **83.24 个百分点**。对 1,274 个完整组进行 2,000 次成对 bootstrap，准确率差的 95% 区间为 **[81.32, 85.24] 个百分点**。

成对 bootstrap 让两个模型每次抽取相同的完整组，不把同组两题当作彼此独立。这个区间仍受共享政策和模板影响，不能当作真实业务或多次重训的稳定性保证。

### 9.2 候选重排和客户原话变化

再对预先固定的 32 道验证题执行五种输入，两个模型共 320 次辅助推理：

| 输入变体 | 基座正确数 | LoRA 正确数 |
|---|---:|---:|
| 固定候选顺序 | 3/32 | 32/32 |
| 候选重排，seed=7 | 5/32 | 32/32 |
| 候选重排，seed=19 | 10/32 | 32/32 |
| 候选重排，seed=43 | 9/32 | 32/32 |
| 将客户原话替换为中性说明 | 3/32 | 31/32 |

LoRA 在三套重排中没有改变语义动作，但中性化客户原话后，有一题从正确的 `request_info` 变成 `wait`。因此可以说它在已测候选重排上稳定，不能说它完全不受措辞影响。

这 32 题是小规模验证集探针，不是额外独立测试，也没有覆盖所有售后场景。看到最终测试和错误分析后，本次没有继续调参或追加训练。

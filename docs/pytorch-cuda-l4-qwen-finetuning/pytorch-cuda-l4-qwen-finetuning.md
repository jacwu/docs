# 使用 PyTorch + CUDA 在 L4 上微调 Qwen 售后决策模型

本文以 **Qwen3.5-4B 的中文电商售后决策微调**为例，介绍在 NVIDIA L4 上完成环境检查、数据准备、小样本验证、正式训练、概率校准和完整测试的过程。模型根据售后政策、已核实的订单事实和客户原话，从七个动作中选择下一步，不生成长篇客服回复。

本次使用 **CUDA、BF16 基座与 FP32 LoRA 参数**，没有做 4-bit 量化。正式训练覆盖 3,738 道题、1 个 epoch，训练循环约 **1.78 小时**；在相同输入与评分协议下，2,548 道合成测试题的准确率由基座的 **42.27%** 提高到微调后的 **100%**。不过，校准集仍有一条高置信度错题，中性原话稳健性测试也有一条错误；温度校准还让微调模型的测试集概率指标变差。本文同时记录这些限制，不把满分等同于真实业务可靠性。

## 一、确定任务和技术路线

### 1.1 将售后处理定义为七选一任务

输入由三部分组成：

| 输入 | 含义 | 例子 |
|---|---|---|
| `policy` | 当前适用的售后规则与参数 | 证明等级、退款时限、自动处理金额和数量上限 |
| `records` | 已经核实的订单与售后事实 | 扣款次数、缺件情况、退款状态、库存 |
| `message` | 客户的原始描述 | “这单少了一件，能不能补发？” |

模型输出 `next_action`，候选动作固定为七个：

| 动作 | 含义 |
|---|---|
| `refund_only` | 无需退货的退款流程；重复扣款只退多扣部分 |
| `return_refund` | 退货退款流程 |
| `reship` | 补发或换新 |
| `wait` | 等待现有物流或退款流程 |
| `decline` | 按政策拒绝本次申请或重复退款 |
| `request_info` | 补充订单、证明或诉求信息 |
| `manual_review` | 人工核查或确认方案 |

例如，已核实缺件、证明满足要求、客户要求补发且库存充足时，通常应选择 `reship`；如果金额、数量或申请年龄超过自动处理上限，则应改为 `manual_review`。前置规则也必须按政策顺序处理，例如退款已经进行中时不能再次发起退款。

这种设计将“判断”与“执行”分开。模型只返回处理建议和概率，不直接退款或修改订单；客户原话也不能覆盖已经核实的事实。接入业务系统时，仍需要确定性规则校验与人工兜底。

### 1.2 本次采用的训练方式

| 项目 | 方案 |
|---|---|
| 基座 | [Qwen/Qwen3.5-4B](https://huggingface.co/Qwen/Qwen3.5-4B)，使用文本语言模型部分 |
| 计算框架 / 后端 | PyTorch / CUDA |
| GPU | NVIDIA L4，24 GB 级显存 |
| 基座精度 | BF16，16 位浮点数 |
| 可训练参数精度 | FP32 LoRA master 参数 |
| 微调方法 | LoRA，冻结基座，只更新附加的低秩参数 |
| 训练目标 | 七个候选动作的概率分布 |
| 输出方式 | 读取答案位置 token 的 logits，不生成长文本 |

**基座**是微调前的预训练模型；**权重**是神经网络中的数值参数。LoRA 将权重增量表示为两个较小矩阵的乘积，在保留基座的同时学习任务所需的增量。

本次 rank=8、alpha=16，实际可训练参数为 **16,232,448，约 1,623 万**，分布在 **496 个 LoRA 张量**中。没有增加独立的决策头，也没有更新全部 4B 基座参数。

## 二、准备项目环境与 CUDA 加载路径

### 2.1 环境配置

本次实际运行的主要版本如下。这是一组已经验证的组合，不表示其他机器必须追逐相同的最新版本。

| 项目 | 配置 |
|---|---|
| GPU | NVIDIA L4 |
| 系统 / Python | Linux / Python 3.13.15 |
| PyTorch | 2.11.0+cu130 |
| CUDA 运行时版本 | 13.0 |
| Transformers | 5.18.0 |
| PEFT | 0.21.2 |
| Accelerate | 1.15.0 |
| Safetensors | 0.8.0 |
| 设备 / 基座精度 | `cuda:0` / `bfloat16` |

CUDA 是 PyTorch 使用 NVIDIA GPU 的计算后端，不是模型文件格式。PyTorch 的 CUDA 构建版本、GPU 驱动和设备能力需要匹配，不能只看到机器名称就开始训练。

环境准备和预检包括：

1. 将代码、数据、模型缓存和每次实验输出放到明确的项目目录；在自管机器上优先使用独立虚拟环境，并记录实际依赖版本。
2. 检查 GPU 名称、可见显存、`torch.cuda.is_available()` 和 BF16 支持，执行一次 CUDA 张量运算。
3. 下载并核对官方基座文件，固定模型 revision，而不是只记录一个会变化的模型名称。
4. 检查磁盘和显存余量，确认没有另一个训练或评估进程占用同一张 GPU。

本次固定的基座 revision 为 `851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a`。代码、数据、配置和模型文件都记录 SHA-256 指纹，用于核对实验身份。指纹一致证明文件没变，不证明数据标签一定正确。

### 2.2 以 BF16 直接加载到 CUDA

本次把基座以 BF16 直接加载到 CUDA，没有 CPU 权重卸载。加载顺序如下：

1. 读取 tokenizer 和模型配置，从 Qwen3.5 配置中提取文本配置。
2. 使用 `Qwen3_5ForCausalLM` 加载文本语言模型，不进入图像或视频处理流程。
3. 明确指定 `dtype=bfloat16`、`device_map={"": "cuda:0"}`，使用本地已经核验的模型文件。
4. 使用 SDPA 注意力路径；检查所有模型参数与输入位于预期设备。
5. 注入 LoRA，冻结基座，将可训练 LoRA 参数保留为 FP32，再检查梯度路径。

tokenizer 和配置在 CPU 上处理是正常的，并不表示神经网络在 CPU 上训练。本次前向和反向计算使用 CUDA BF16 autocast，即让适用的计算以 BF16 执行；候选 logits、概率和损失转换为 FP32。BF16 路径没有启用 FP16 用的 GradScaler 损失缩放。

部分可选融合内核没有参与本轮计算，使用 PyTorch 参考实现完成。出现这类提示不等于训练失败，也不能把未启用的优化内核写成已经使用。

### 2.3 先排查加载兼容性，再开始长训练

首次尝试在 PEFT 与预装 `torchao` 的可选兼容分支失败，当时 **零次参数更新**。由于本次不使用该量化后端，随后修正了不需要的可选加载分支，在新的实验目录重新执行 BF16 方案，并保留原失败记录。

这类问题应先确定“当前方案实际依赖什么”，再修正兼容路径。不能把依赖加载失败解释为数据训练失败，也不能覆盖旧目录后把两次尝试混称为一次成功运行。真正的代码或配置变化必须形成新的实验身份。

训练、评估由独立 Python 子进程执行，操作面板负责提交和查看状态。判断进度时同时检查真实进程、持续日志、完成凭证和备份，而不是只看一段旧输出。GPU 阶段串行运行，避免重复启动。

## 三、准备电商售后数据集

### 3.1 数据集的用途与文件

本文使用的[完整售后数据集](datasets/after-sales/)覆盖缺件、损坏、物流延迟、重复扣款、取消订单、无理由退货、退款处理中、风险冲突和自动处理上限等情况。训练前固定数据、标签与四份划分，运行过程中不再修改。

这些记录根据**虚构的售后政策**合成，答案由规则生成，不是真实客户对话，也不代表某个电商平台的实际政策。独立人工审核尚未完成，因此它首先是一份学习和实验数据。

| 数据划分 | 题数 | 完整组数 | 唯一用途 |
|---|---:|---:|---|
| [train](datasets/after-sales/train.jsonl) | 3,738 | 1,869 | 更新参数；固定抽取工程诊断与试跑子集 |
| [validation](datasets/after-sales/validation.jsonl) | 1,512 | 756 | 比较正式模型与基座的开发分布表现 |
| [calibration](datasets/after-sales/calibration.jsonl) | 1,512 | 756 | 模型锁定后拟合概率温度 |
| [test](datasets/after-sales/test.jsonl) | 2,548 | 1,274 | 模型与温度锁定后的最终测试 |
| 合计 | 9,310 | 4,655 | 四份独立记录集合 |

**JSONL** 是一行一个 JSON 对象。配套的[政策定义](datasets/after-sales/policy_spec.json)描述规则，[评估切片](datasets/after-sales/evaluation_slices.json)规定不同场景的统计范围。

validation 与 calibration 题目不同，作用也不同：前者检查模型表现，后者只拟合输出概率的温度。两者都不参与基座或 LoRA 的梯度更新，不能在校准时偷偷继续训练模型。

### 3.2 一条售后训练样本

下面节选自训练集的缺件补发案例，仅保留部分字段。完整模型输入还包含政策规则、问题说明和七个候选动作，以原始数据为准。

```json
{
  "case_id": "as4-e32b9350124204fbb17b-v0",
  "group_id": "as4-e32b9350124204fbb17b",
  "split": "train",
  "request": {
    "state": {
      "message": "我反馈的是少件问题，麻烦核对这单记录。",
      "policy": {
        "parameters": {
          "age_limit": 30,
          "amount_limit": 1200,
          "evidence_min": 3,
          "units_limit": 3
        }
      },
      "records": {
        "affected_units": 1,
        "amount_yuan": 938,
        "claim": "missing",
        "conflicting_records": false,
        "evidence_level": 3,
        "fraud_risk": false,
        "order_verified": true,
        "paid_copies": 1,
        "refund_status": "none",
        "request_age_days": 0,
        "requested": "replacement",
        "stock": true
      }
    }
  },
  "targets": {
    "next_action": {
      "type": "choice",
      "hard_label": "reship"
    }
  }
}
```

该记录表示：已核实缺件，证明等级 3 满足要求；客户要求补发且有库存；金额 938 元、件数 1、申请年龄 0 天都没有超过自动处理上限，因此目标是 `reship`。

`targets.next_action.hard_label` 是监督答案，只用于损失和离线评价，**不能进入提示词**。`case_id` 和 `group_id` 用于追踪与分组，也不作为模型输入。原始数据另有其他监督字段，但本次只训练 `next_action`；原请求中的模型元数据不决定本次实际加载的基座。

### 3.3 为什么题数是完整组数的两倍

每个完整组包含两道相关题，用来观察关键条件改变后的行为：

- **反事实组**：改变关键事实或政策，正确动作应改变，例如把自动金额上限调低到本次金额以下。
- **不变性组**：改变不影响当前决策的因素，正确动作应保持不变。

同组两题不能拆到不同集合；评价“完整组正确”时，必须两题都正确。只把它们当作独立题目，可能掩盖模型不能跟随条件变化的问题。

本轮实际随机训练呈现的最大输入是 **858 tokens**，固定候选顺序预检最大为 **860 tokens**，均低于 1,024，没有截断。token 数应使用当前 tokenizer 和实际提示词计算，确保政策和订单字段完整保留。

## 四、把售后样本转换为模型输入和监督目标

### 4.1 用答案位置读取七个候选的分数

模型不是直接生成 `reship` 这个字符串，而是将候选映射到 `A`—`G`，从提示词最后位置预测下一 token 的词表分数中取出七个答案位置的 **logits**，再映射回动作。

logits 是概率归一化前的分数，数值越大表示模型越偏向该候选。对七个分数计算 softmax，得到总和为 1 的候选概率，再选择最高概率的动作。

开始前必须确认 `A`—`G` 各自对应一个独立 token，且七个 token ID 互不相同。动作名称是业务语义，不一定是单 token，不能直接把动作字符串当作一个词表索引。

这种方法使用原语言模型的输出头，没有另建分类头；输出概率只在这七个候选中归一化，也不是整张词表或所有自然语言回答的概率。

### 4.2 重排候选时，目标也必须重排

转换每条样本时，执行以下步骤：

1. 读取状态、问题和七个候选说明，不读取监督答案作为输入。
2. 按当前候选顺序分配 A—G，保持动作和说明对应。
3. 应用聊天模板，关闭思考模式，分词并检查长度；不静默截断。
4. 根据正确动作的位置生成 **one-hot 目标**：正确项为 1，其余六项为 0。

假设候选顺序为 `decline、manual_review、refund_only、request_info、reship、return_refund、wait`，则补发样本的目标是 `[0, 0, 0, 0, 1, 0, 0]`。重排候选后，目标必须跟随动作移动，不能沿用旧位置。

训练采用随机候选顺序，以 seed=42 为基础结合轮次和样本行号生成可复现的排列；主验证、校准和测试采用固定顺序，另做重排稳健性测试。其他文本增强和额外候选填充关闭。

学习重点是让模型学习“条件对应什么动作”，而不是“第五个位置通常正确”。如果候选与标签错位，即使训练损失下降，也可能是在学习错误监督。

## 五、配置 LoRA 与训练损失

### 5.1 只更新文本模型的 LoRA 参数

本次按完整模块路径选择文本模型中的线性投影层，排除词嵌入和语言模型输出头，避免短名称匹配误选同名模块。PEFT 注入 LoRA 后，确认只有预期的 16,232,448 个参数参与训练。

| 参数 | 本次值 | 含义 |
|---|---:|---|
| rank | 8 | LoRA 低秩矩阵的内部维度，不是量化位数 |
| alpha | 16 | 标准 LoRA 更新的缩放参数，本次 alpha/rank=2 |
| dropout | 0.05 | 训练时的随机失活比例，评估时关闭 |
| 基座参数 | 冻结 | 不参与优化器更新 |
| LoRA master 参数 | FP32 | 可训练参数保留较高精度，前向配合 BF16 autocast |

训练开启 **gradient checkpointing（梯度检查点）**：不保存所有中间激活，反向传播时重算部分结果，以额外计算换取显存。它与把模型文件保存到磁盘的 checkpoint 不是同一概念。

同时关闭推理用的 KV 缓存，检查输入激活能够承载梯度，避免“基座被冻结后，LoRA 也没有正常收到梯度”的工程问题。

### 5.2 CE + Brier 监督七个候选概率

本轮损失为 `CE + Brier`，两项权重都为 1：

- **CE，交叉熵**：one-hot 标签下是正确动作概率的负对数，正确项概率越低，惩罚越大。
- **Brier**：七个预测概率与 one-hot 目标之差的平方和；本次按七类求和，没有再除以 7。

候选分数、概率和损失用 FP32 计算。监督发生在下一答案位置，而不是要求模型复述政策、拟合整段输入或生成客服话术。

训练损失下降说明模型正在拟合训练目标，不自动证明泛化有效。保存正确、重载一致、完整保留集优于基座分别回答不同的问题，不能互相替代。

### 5.3 梯度累积与学习率

| 训练参数 | 正式训练值 |
|---|---:|
| epoch | 1 |
| 最大输入长度 | 1,024 tokens |
| micro-batch | 1 |
| 梯度累积 | 8 |
| 峰值学习率 | 1e-4 |
| warmup 比例 | 0.03，转换为 14 步 |
| 学习率计划 | warmup 后余弦衰减 |
| 优化器 | AdamW，weight decay=0 |
| AdamW betas / epsilon | (0.9, 0.95) / 1e-8 |
| 梯度范数裁剪上限 | 1 |
| 随机种子 | 42 |
| 保存间隔 | 每 50 次优化器调用及最终结束 |

micro-batch=1 表示一次前后向处理一道题；梯度累积=8 表示累计八题的梯度后调用一次优化器，通常对应八题的有效批量。梯度裁剪限制的是整体梯度范数，不是把每个参数都限制到 1。

最后不足八题的尾批按实际题数归一化，避免尾批梯度被额外缩小。学习率统计记录优化器调用时真正使用的值，不能拿调用后更新的“下一步学习率”代替它。

## 六、先做小样本验证，再进行完整训练

### 6.1 32 题 smoke：证明工程链路有效

**Smoke test（冒烟测试）**先检查最小训练链路能否完整运行，不用于宣布模型效果。

本次使用固定 32 道训练题，4 次优化器调用，其中 3 次学习率为正。确认冻结基座指纹不变，496 个 LoRA 张量全部改变且保持有限值，再保存 adapter，交给新进程重载。

固定 4 道参考题的重载 logits 最大绝对差为 **0.0**。这证明保存文件能重现本次参考结果，不代表所有机器、精度和内核都会逐位相同，也不证明测试准确率提高。

### 6.2 8 题诊断：刻意拟合，不冒充泛化

**Overfit 诊断**刻意反复训练少量题，检查模型是否能学会它们，以及候选位置重排是否影响学习。每个节点重新初始化基座和 adapter，不从前一节点继续训练。

实际执行的预设分支为 `R40 → F40 → RC40 → RC160`：R/F 表示随机/固定候选顺序，C 表示常数学习率；没有 C 的节点使用预热和余弦衰减。

| 节点 | 调用次数 | 固定顺序评分 | 结论 |
|---|---:|---:|---|
| R40 | 40 | 7/8 | 未通过 |
| F40 | 40 | 8/8 | 固定模式通过，但不能替代随机关卡 |
| RC40 | 40 | 7/8 | 三套额外重排也各 7/8，未通过 |
| RC160 | 160 | 8/8 | 固定顺序及 seeds 7/19/43 均 8/8，通过 |

累计实际使用 280 次诊断调用，没有重置预设的 600 次 / 12 小时预算。RC160 的 1,280 次样本呈现、参数变化、冻结基座和参考重载都完成复核。

这些节点共同证明该实现能够学习小样本任务，不构成严格的单因素因果实验，也不能用 8/8 替代独立保留集测试。

### 6.3 196 题 pilot：估计时间与显存

**Pilot（试跑）**使用接近真实长度的数据，估计完整训练成本，并检查尾批、保存和资源占用。

本次固定 196 道题、98 个完整组，新基座和新 adapter，25 次优化器调用，尾批 4 题。循环耗时约 **335.79 秒**；稳定区间 19 步的耗时中位数为 **13.7244 秒**，外推 468 次调用约 1.784 小时。

预测不包括完整评估、模型加载、备份和文件传输，也不是保证完成时间。试跑模型不作为正式模型的起点。

### 6.4 从新基座完成一轮正式训练

正式训练重新加载原始基座，创建全新 LoRA，不继承 smoke、诊断或 pilot 参数。一轮完整遍历 3,738 道题，共 1,869 个完整组。

3,738 = 467×8 + 2，所以需要 **468 次优化器调用**，最后两题构成尾批。由于预热计划的首次实际学习率为 0，实际是 **467 次正学习率调用**；不是漏训练一批，也不是训练了 468 道题。

训练循环实测 **6,397.31 秒，约 1.78 小时**，单次更新耗时中位数为 **13.7015 秒**。独立验收重新渲染全部训练呈现，核对题目、候选、目标、随机种子、token 数和提示词哈希；逐项复算 468 次实际学习率。

所有记录的损失与梯度有限，梯度范数为正；冻结基座指纹不变，496 个 LoRA 张量全部改变且最终有限。每 50 次调用保存中途 adapter，但训练前约定的**唯一正式候选是最终 checkpoint**，不根据验证或测试结果挑中途模型。

## 七、保存、重载与实际推理

### 7.1 保存的是 adapter，不是完整 4B 模型

最终交付包括 `adapter_model.safetensors`、`adapter_config.json`、tokenizer 文件和聊天模板；另保存训练参数、更新审计、数据与代码指纹、预测记录和评估报告。

最终 adapter 权重大小为 **64,996,408 字节，约 61.99 MiB**，SHA-256 为：

```text
3bbc29ac5448dd2fa08bd41f712a55fb24e23ee5fe544f8e9bb60fb755f435e3
```

adapter 只是学习到的附加参数，不包含完整基座。使用它时必须加载匹配的 `Qwen/Qwen3.5-4B` 基座，再注入 adapter；只下载这个约 62 MiB 的文件不能独立运行模型。

中途 adapter checkpoint 没有包含完整 AdamW 动量、scheduler 和随机数状态，不能称为可精确断点续训的完整训练 checkpoint。已完成阶段可以核验后跳过；部分失败阶段则必须保留证据并明确恢复方案，不能直接覆盖继续。

### 7.2 用新进程检查保存结果

正式训练后，用新进程加载匹配基座和最终 adapter，将模型置于评估模式，关闭 dropout，再评分预先固定的 4 道参考题。

保存前后 logits 的最大绝对差为 **0.0**。同时核对候选顺序、提示词和 tokenizer 身份，避免“结果不同”其实来自输入变化，或“结果相同”其实只是沿用了内存中的旧模型。

阶段输出备份到持久存储，并逐文件核对大小、SHA-256 和完成凭证。显示“复制完成”还不够；本次最终运行目录的持久副本与原目录通过全量文件核对，最终 adapter、报告及验收材料也已经下载到本地。

### 7.3 一次实际调用返回什么

完整评估和验收后，再用新进程真实加载基座加最终 adapter，调用一条验证集样本。该样本已核实缺件、证明满足要求、希望补发且有库存，无风险或记录冲突；金额 105 元不超过 200 元、数量 2 不超过 3、申请年龄 2 天不超过 5 天，正确动作是 `reship`。

本次实际输出可摘要为：

```json
{
  "action": "reship",
  "raw_reship_probability": 0.9999766538654733,
  "calibrated_reship_probability": 0.9994471436855051,
  "inference_seconds": 0.8440211689994612
}
```

这段是实际结果的摘要，不是 REST API 协议。约 0.844 秒是该次输入评分耗时，不含模型加载，不能作为通用服务吞吐量或延迟基准。

本轮调用方式是 Python 程序：加载基座与 adapter → 构造提示词 → 模型前向 → 读取七个候选分数 → 按需应用温度 → 返回动作和概率。没有启动 REST 服务，没有生成长回复，也没有真的执行补发。

正常推理输入不需要 `targets`；示例保留答案只是为了离线核对。将来如果包装为接口，接口层是另一个工程步骤，并不会改变 adapter 本身的含义。

## 八、与基座比较，并校准输出概率

### 8.1 使用完全相同的评分协议

微调是否有效，不能只看训练 loss 或一条示例。基座和微调模型使用相同数据、提示词、候选顺序、tokenizer 与评分逻辑，分别完成完整 validation、calibration 和 test。

两模型的 validation 各有 1,512 道题，结果如下：

| 指标 | 基座 | LoRA |
|---|---:|---:|
| 正确数 | 666/1,512 | 1,512/1,512 |
| Accuracy | 44.0476% | 100% |
| Macro-F1 | 0.416800 | 1 |
| CE | 1.484329 | 0.000040021 |
| Brier | 0.698296 | 2.8975×10⁻⁸ |
| ECE10 | 0.122784 | 0.000040012 |
| 完整组两题都正确 | 233/756 | 756/756 |

**Accuracy** 是总体正确比例；**precision** 看预测为某类的题有多少真正属于该类，**recall** 看该类正确题被找回多少，**F1** 综合两者；**Macro-F1** 对七类 F1 等权平均，避免大类掩盖小类问题。

**ECE10** 将置信度划入十个区间，对比每个区间的平均置信度和实际正确率。它是总体近似指标，不保证每个高置信度个案都正确。

这里评价的是特定七选一协议下的微调效果，不代表基座的通用问答能力，也不能把结果写成模型通用能力排名。

### 8.2 模型锁定后，单独拟合温度

确定唯一最终 adapter 后，用另一份 1,512 题 calibration 集分别拟合两模型的温度 **T**。程序将原 logits 除以 T，再计算 softmax：`softmax(logits / T)`。

T>1 通常让分布更平缓，T<1 让分布更尖锐。正温度不改变分数排序，所以不会修复错误动作或提高 argmax 准确率。

| 模型 | 校准集正确数 | 冻结温度 T | 校准集 CE：raw → calibrated |
|---|---:|---:|---:|
| 基座 | 663/1,512 | 1.3478842359054866 | 1.551158 → 1.518877 |
| LoRA | 1,511/1,512 | 1.3496787500692344 | 0.007275 → 0.006009 |

本次在预先固定的 [0.1, 10] 范围内，以校准集平均 CE 为目标拟合；两个温度都在区间内部，独立复算确认逆温度导数接近 0。拟合过程不使用 test，不重新更新权重。

温度可以保存为 JSON 配置，但必须由调用程序明确读取和应用。模型不会自动寻找任意 JSON 文件；修改配置也不等于改了神经网络参数。

这里的 temperature 是分类概率的事后校准参数，不是自由文本生成时为了控制随机性的采样温度。校准集上的 CE 变好，也不保证新集合上的概率指标一定变好。

### 8.3 校准不能修复漏判业务条件

校准集唯一的 LoRA 错题很有说明性：已核实缺件、证明等级满足要求，申请退款；金额 485≤800、申请年龄 8≤21，但受影响数量 **3 超过 units_limit=1**，按规则必须 `manual_review`。

模型却以 **99.9758%** 的原始概率选择 `refund_only`，正确人工复核的概率约为 **0.00178%**。这是可观察的数量上限漏判，不能因为总体准确率高而忽略。

温度只能软化这条错误预测的概率，不能把动作改对。要改善这种问题，需要新的数据覆盖、训练实验或业务规则校验，而不是把“概率校准”当成“业务纠错”。

## 九、完整测试结果与剩余问题

### 9.1 四种 raw / calibrated 结果

模型和温度锁定后，基座与 LoRA 各完成 2,548 道 test，共 5,096 条原始预测。四种结果由两套 logits 在 CPU 上分别计算原始和校准概率，不需要为了四张表重复跑四次 GPU 评分。

| test 版本 | Accuracy | Macro-F1 | CE↓ | Brier↓ | ECE10↓ |
|---|---:|---:|---:|---:|---:|
| 基座 raw | 42.2684% | 0.404169 | 1.584591442 | 0.742059536 | 0.116931705 |
| LoRA raw | 100% | 1 | 0.000040388 | 1.8629×10⁻⁸ | 0.000040382 |
| 基座 calibrated | 42.2684% | 0.404169 | 1.539641316 | 0.725809477 | 0.112233816 |
| LoRA calibrated | 100% | 1 | 0.000631847 | 1.6094×10⁻⁶ | 0.000631278 |

基座正确 1,077 题，LoRA 正确 2,548 题，raw 准确率提升 **57.7316 个百分点**。两者都对 1,077 题，基座错而 LoRA 对 1,471 题；本次 test 中不存在“基座对而 LoRA 错”或“两者都错”的案例，不另外编造测试退步示例。

但 **LoRA 校准后的 test CE、Brier、ECE10 均比自身 raw 更差**。校准集有一条极高置信度错题，拟合得到 T>1；而 test 恰好全部正确，降低正确项置信度反而增加这些误差。这是与数据一致的解释，不是对模型内部机制的证明。

本轮如实保留该负结果，没有看完 test 后重拟合 T，也没有把 T 改回 1 冒充原协议结果。校准模型仍优于基座，不代表校准步骤相对未校准模型也改善了。

|---|---:|---:|---:|

| return_refund | 12.3626% | 0.203160 | 100% / 1 |

动作一致率必须与正确率一起看：始终选择同一个错误动作也可能非常一致。正温度校准不改变这些动作指标。

### 9.3 用完整组 bootstrap 估计差异

**Bootstrap** 是对评价数据反复有放回抽样，估计指标差异在当前样本下的波动。本次以 1,274 个完整组为单位，每次同时取出组内两题，并对基座和 LoRA 使用相同抽样。

执行 2,000 次重采样、seed=42 后，raw 准确率提升的 95% 区间为 **[+55.6122, +60.0481] 个百分点**。

这个区间是当前合成数据下的条件估计，不表示“模型有 95% 的概率在任何真实业务中改善”，也不包含重新训练的随机种子波动或外部政策变化。不能把相关的两题拆散后伪装成更多独立证据。

### 9.4 稳健性测试：满分仍有措辞敏感

从 validation 固定抽取 32 道题、16 个完整组，测试五种输入：原顺序、三套候选重排，以及将客户原话替换为中性句子。两个模型共完成 **32×5×2=320 条评分**。

| 变体 | 基座正确数 / 32 | 基座动作翻转率 | LoRA 正确数 / 32 | LoRA 动作翻转率 |
|---|---:|---:|---:|---:|
| 原顺序 | 17 | 0 | 32 | 0 |
| 候选重排 seed=7 | 14 | 34.375% | 32 | 0 |
| 候选重排 seed=19 | 14 | 25% | 32 | 0 |
| 候选重排 seed=43 | 14 | 21.875% | 32 | 0 |
| 中性原话 | 15 | 18.75% | 31 | 3.125% |

翻转率以同一模型的原顺序预测为参照，既可能是变好，也可能是变坏，需同时看正确率。本次 LoRA 的候选重排全部通过，但中性原话导致一题由正确变错误。

该题已核实两次扣款，无风险、无记录冲突、无进行中或已完成退款；金额 524≤800、数量 3≤8、申请年龄 7≤21，按规则应 `refund_only`，只退多扣部分。

原话为“支付页面卡过一次，后来又点了一遍，担心付重了。”时，模型正确退款概率为 **99.9947%**；保持事实和政策不变，只改为“请根据已核实的records和policy处理。”后，却选择 `request_info`，概率 **67.4512%**，正确退款概率降到 **31.8617%**。

这说明模型仍对不应改变本题结论的措辞敏感。探针仅有 32 道题，未覆盖所有场景，不能称为完整鲁棒性认证，更不能因为主 test 满分而省略这个错误。

### 9.5 独立验收与结果边界

最终独立 CPU verifier 重新渲染输入、核对身份，并复算记录中的 logits、目标和指标，覆盖：

- 3,738 次正式训练呈现、468 次实际优化器调用及学习率。
- 两模型各完整 validation / calibration / test，共 11,144 条主评分。
- 四组 raw / calibrated 概率、七类指标、17 个切片和完整组指标。
- 两个温度、2,000 次完整组 bootstrap 和 320 条稳健性评分。
- 最终参数身份、完成凭证和交付文件；另核对冻结基座、LoRA 变化与新进程参考重载。

本地再次完成文件验收和 CPU 指标复算。**复算记录中的 logits，不等于重新执行 4B 模型前向。** 模型实际加载和调用已在 L4 上验证；若更换设备、精度或推理框架，应另行验证加载路径和输出一致性。

这些结果证明本次工程链路有效、当前合成任务显著改善；不能证明真实客户、未知政策或新措辞同样可靠。四份集合仍共享政策和模板，标签是规则生成的，也只有一个正式训练种子。

看到 test 后不再追加训练、换提示词、重拟合温度或重选 checkpoint。后续改善数量上限和措辞敏感问题，应建立新实验，并准备新的未见评价数据。

### 10.2 显存如何使用

正式训练记录中的 CUDA allocated 最大采样值约为 **8.7653 GiB**。这是 PyTorch 已分配张量显存的采样值，不等于整机内存峰值、驱动总占用或所有时刻的精确峰值，也不意味着任意 4B 训练只需要这么多显存。

显存主要用于冻结的 BF16 基座、FP32 LoRA 参数及其梯度和优化器状态、中间激活与计算临时张量。虽然基座不更新，它仍需驻留并参与前后向；LoRA 文件小不代表训练内存等于文件大小。

本次最大长度 1,024、micro-batch=1，并开启梯度检查点。扩大长度或微批量可能明显增加显存。若资源不足，应在新实验中评估缩短输入、减小批量或 QLoRA，而不是途中改变精度却继续沿用原结果。
